# 게시글 삭제 정책 선택 이유

## Soft Delete란?

- 데이터를 실제로 데이터베이스에서 제거하지 않고, `deleted_at`이나 `is_deleted`와 같은 컬럼를 두어 논리적으로 "삭제된 상태"로 표시하는 방식
- 사용자 화면에서는 삭제된 것처럼 보이지만, 실제 레코드는 DB에 그대로 남아있으며 일정 기간 후 복구하거나 영구 삭제(Hard Delete)할 수 있다.

## Hard Delete란?

- 사용자가 삭제 요청을 하는 즉시 해당 레코드를 DB에서 물리적으로 완전히 제거하는 방식
- 한 번 삭제되면 복구가 불가능하며, DB 용량 관리 측면에서는 유리하지만 사용자 실수나 악의적 삭제에 대한 대응이 어렵다.

## Soft Delete vs Hard Delete

| 구분             | Soft Delete             | Hard Delete                 |
|----------------|-------------------------|-----------------------------|
| **복구 가능성**     | 유예기간 내 복구 가능            | 복구 불가능                      |
| **사용자 경험**     | 실수 삭제에 대한 안전장치 제공       | 복구 수단 없음, 실수에 취약            |
| **구현 복잡도**     | 조회 쿼리마다 삭제 여부 필터링 필요    | 단순 DELETE로 구현 간단            |
| **저장 공간**      | 삭제 데이터도 계속 저장되어 용량 증가   | 즉시 공간 확보                    |
| **성능**         | 인덱스/쿼리에 조건 추가로 약간의 오버헤드 | 상대적으로 가벼움                   |
| **개인정보/법적 이슈** | 일정 기간 데이터 보관 시 정책 수립 필요 | 즉시 파기로 법적 리스크 적음            |
| **연관 데이터 처리**  | 참조 무결성 유지 용이 (연쇄 삭제 방지) | 연관 데이터 처리(cascade) 별도 설계 필요 |

## 나의 선택과 근거

- 현재 Dive가 벤치마킹하고 있는 SNS 앱은 인스타그램이다.
- 인스타그램은 최근 삭제한 콘텐츠 탭에서 30일 이내에 일반 게시글을 복구할 수 있다.
- 따라서 Soft Delete로 구현하되, 30일의 유예 기간을 주기로 했다.

# (추가) 댓글 삭제 정책

- 게시글을 soft delete하기로 했던 가장 큰 이유는 유저의 편의를 위해서였다. 오랜 기간 공들여 쓴 게시글이 한번의 실수로 인해 삭제되는 것을 방지할 수 있기 때문이다.
- 이 관점에서 댓글의 경우도 생각해보았다. 댓글은 게시글보다는 평균적으로 작성 부담이 적고 내용이 적다고 판단했다.
- 따라서 유저의 편의보다는 soft delete의 단점(저장 공간 증가, 약간의 성능 오버헤드 등)이 더 크다고 판단했고 따라서 댓글의 경우 hard delete로 삭제하기로 결정했다.
